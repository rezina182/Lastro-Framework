Por que o LASTRO existe

Com IA, o código sai mais rápido do que a revisão acompanha. E os erros de sempre voltam: TLS desligado, SQL montado com texto, senha fixa no código, cookie sem proteção, ação do CI que qualquer um pode trocar.

Instrução em texto não garante

"Não faça isso" no prompt ajuda, mas o modelo pode esquecer, entender errado ou ser enganado por um arquivo malicioso. Regra que só existe dentro do modelo não é controle.

O que obriga fica fora do modelo

A IA é orientada por regras e skills. Quem garante é verificação determinística: hooks no editor, o portão no CI e a prova registrada, com nome e prazo de validade.

Como funciona

Cinco passos, sempre os mesmos, para uma aplicação nova ou para uma que já existe.

1

Entende a aplicação

Lê o código e monta o perfil: tem login, upload, dado pessoal, tempo real? Cada resposta decide quais controles valem.

lastro init
2

Mede

Verifica o repositório e, se você quiser, a aplicação rodando em local ou staging, inclusive com duas contas de teste.

lastro check
3

Explica

Nota de 0 a 10, por que ela está assim e o próximo passo. Controle sem prova conta zero.

lastro gaps
4

Mostra

Um portal estático com os números, as decisões para agora e o detalhe de cada controle.

lastro site
5

Corrige e prova

Correção previsível numa branch nova, roteiro de cada teste manual e o registro de quem testou e até quando vale.

lastro fix

A IA trabalhando junto, com trava

O adaptador do Kiro instala um time pronto no projeto. O agente prepara; quem decide e publica é você.

1

Agente lastro

Pergunta se a aplicação é nova ou existente. Na nova, entrega requisitos, ameaças e testes antes do código. Na existente, mede, corrige, prova e prepara o PR. Não pode fazer commit, push nem abrir PR.

5

Skills por tarefa

lastro-requisitos, lastro-triagem, lastro-corrigir, lastro-testes e lastro-pr. O Kiro carrega cada uma quando o pedido combina, ou com /nome.

7

Steering

As regras de sempre (rodar o check antes de terminar, nunca atestar nem aceitar risco sozinho) e as de cada assunto: autenticação, dados, web, upload, tempo real e revisão de ameaças.

3

Hooks

lastro-protect pede confirmação antes de mexer nas decisões; lastro-publish bloqueia push e PR vindos do agente; lastro-stop roda o check quando o agente termina.

Como ativar

# na pasta do seu projeto
node /caminho/lastro/verifier/bin/lastro.js adapter kiro          # mostra o que seria criado
node /caminho/lastro/verifier/bin/lastro.js adapter kiro --write  # cria em .kiro/

Depois, escolha o agente lastro no seletor de agentes do chat. Nada é sobrescrito: arquivo que já existe fica como está.

O ciclo com IA (AI-DLC)

  • Aplicação nova: requisitos, decisões de arquitetura, ameaças e testes de cada funcionalidade antes da primeira linha.
  • Aplicação existente: medir, triar, corrigir numa branch, transformar teste manual em teste automático e preparar o PR.
  • Sempre: o check roda ao fim de cada tarefa, e decisão de risco é de uma pessoa.

Como ele aprende

Cada aplicação que passa pelo LASTRO deixa lições: o que a aplicação errou, o que o kit errou e o que o ambiente impediu de testar. Cada lição vira controle, verificação automática ou correção com teste.

App A

Senha fixa nas contas criadas

O cadastro pelo administrador usava uma senha padrão escrita no código. Virou a verificação AUTH-043, que acha o literal sem nunca mostrar o valor.

App A

CSRF calibrado pelo cookie

Com cookie de sessão SameSite=Strict, a falta de token é defesa em profundidade, não falha alta. O kit passou a medir a gravidade pelo cookie.

App B

Limite com chave do atacante

O limitador de requisições usava como chave um valor que o cliente controla. Virou os controles WEB-011 e WEB-017.

Pesquisa

Arquivos de instrução são vetor de ataque

Instruções do agente mudam o que ele faz. Por isso pedem dono de revisão no CODEOWNERS e hooks fora do modelo.

Regras que não mudam

  • Sem prova não é aprovado: controle sem evidência conta zero.
  • Erro dentro de uma verificação vira "sem prova", nunca "passou".
  • Teste manual exige atestação com responsável e validade de até 366 dias.
  • Risco aceito exige dono, aprovador, justificativa e validade.
  • Decisão é de uma pessoa: o agente propõe, alguém confirma.
  • Sondas na aplicação só em local ou staging, com confirmação explícita.

Comece agora

Requer Node 22 ou mais novo. Nada para instalar.

# dentro do projeto que você quer verificar
node /caminho/lastro/verifier/bin/lastro.js init      # perfil derivado do código
node /caminho/lastro/verifier/bin/lastro.js check     # veredito e nota de 0 a 10
node /caminho/lastro/verifier/bin/lastro.js gaps      # por que a nota está assim
node /caminho/lastro/verifier/bin/lastro.js site --out ../portal   # o portal, para abrir no navegador
